# Calendar automation principals

2026-10-12. Account permission prerequisite; calendar connectors and scheduling are not yet complete.

A login session and an approved background automation are separate principals. Logging out must
revoke interactive access without forcing calendar capture to depend on a stored browser login.
Account now owns explicitly consented `calendar_capture` operation grants, scoped to workspace,
owner and an opaque connection reference. Only the consenting user's authenticated gateway path
can create/revoke them. They remain active until explicit revocation/disconnection; membership
revocation and workspace blocking also deny new work. No tracking code grants authority.

Contracts, authenticated under `/api/v3/workspaces/{workspaceId}`:

- `GET /automation-grants`: current user's grants only.
- `POST /automation-grants`: idempotency key and `{connectionId,consent:true}`.
- `POST /automation-grants/revoke`: idempotency key and `{grantId,expectedVersion}`.

Grant IDs are generated by Account. Replaying a creation response after revocation returns
the current inactive record, not an old active snapshot. Another user or tenant cannot use it.
Integration must validate ownership of the corresponding OAuth connection before activating
scheduled capture. Consent to capture never authorizes external task writes or sharing.

The signed internal actor retains owner/workspace IDs and includes `operationGrantId`, with a
reserved `operation:{grantId}` principal label. That label is not a WorkOS login or bearer credential.
Every hop still requires a pinned service key, exact audience and short expiry. Account evaluates
the current stored grant and membership, not the label. Signed Integration/Workspace/Ingest hops
may use the calendar grant only for current own membership and capture-usage operations. Public
Workspace/Ingest user routes reject operation principals. Grant mutation, directory enumeration
and membership editing remain interactive-only. No new unauthenticated capture endpoint exists.

Ingest stores the grant reference with its durable request so recovery cannot silently convert
an operation into a fake unrevoked login. Cleanup-only reservation lookup/settlement can finish
after logout or grant revocation; it cannot start a new capture or disclose meeting content.

Tests cover consent, idempotency, tenant/owner scope, logout, revocation, capability restrictions,
current-state replay, reserved-principal validation and the actual gateway-to-Account route.

Open work before enabling automation: Integration-owned OAuth connections/tokens and disconnect
cleanup, grant lifecycle UI, authenticated scheduled-capture entrypoint, occurrence reconciliation,
calendar policy checks and cancellation. Provider admission controls remain independent: this
mechanism does not bypass Meet/Zoom/Teams host restrictions. Do not call calendar capture complete
merely because operation-principal tests pass.
