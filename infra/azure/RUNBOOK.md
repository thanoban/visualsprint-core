# Authorized future Azure rollout and qualification

No commands in this runbook were executed against Azure. Every Azure provisioning, DNS migration, provider registration, email/model/capture call and production cutover needs the owner's explicit authority and cost approval. Compile/parameter checks alone are not a deployment recommendation.

## Sequence

1. Approve the exact regional topology/cost, resource providers, HA-zone/PG17/Container Apps quotas, private origin availability and model/email region requirements. Reserve stable owned app/API hostnames. Separate staging and production prefixes/resource groups/data/keys/provider registrations; do not reuse production data as a test fixture.
2. Establish an operator-owned federated GitHub deployment identity and approved ACR/provisioning vault. Review resource-scoped deployment/role-assignment rights, eliminate broad permanent subscription Owner, and configure a VNet-reachable trusted migration/operator agent. These dependencies are not fabricated by this package.
3. Run local `validate.mjs`, isolated owning tests and all service/API/event compatibility/image scans. Pin official base images and final digests; promote the same native/web image digests, never rebuild secretly during production promotion. The frontend is a separate static app image, not gateway HTML catch-all.
4. Fill a private ignored parameter file with real IDs and ARM provisioning-vault references. Leave runtime, edge, bootstrap/migration/maintenance flags false. Offline validation cannot test actual permissions or secret contents. After separate authorization, infrastructure deployment creates paid foundation resources; inspect private DNS/egress and HA before runtime activation.
5. From the approved private operator path, populate each vault with distinct service runtime/migration credentials, service private keys, token encryption keys and necessary provider secrets. Bootstrap administrator credentials match secure provisioning parameters. Runtime/migration DSNs use private hostname verification, never localhost, public PG, sslmode=require or disabled validation.
6. Enable **manual** bootstrap Job definitions with the digest-pinned bootstrap image and per-database secret versions. Start each explicit job once and inspect safe completion status. Jobs are not auto-run by deployment. Scripts whitelist databases, reject unexpected owners/elevated existing roles, create separate non-owner runtime/owning migration roles and revoke public database/schema access. Do not use this as a legacy user/password reset tool. An unexpected estate stops for review, not destructive repair.
7. Enable manual owning migration Job definitions; run Account then each independent cell database and OpenFGA engine migration. Every native service keeps its checksummed existing migration history. OpenFGA migration is separate from `authz_application`. Enable manual maintenance definitions and run `fga-grants` **after** engine migration; runtime cannot write `goose_db_version`. Run `vector` as administrator before opting into Intelligence extended migrations; the foundation only allowlists VECTOR, it does not install the extension. [Azure extension allowlisting](https://learn.microsoft.com/en-us/azure/postgresql/extensions/how-to-allow-extensions).
8. Populate/validate the complete native runtime inventory and caller-pinned trust matrix. Review every optional background/model/email/capture flag. Enable native runtime definitions, verify private API and cross-environment Account → Ingest signed callbacks, unauthenticated denial and database role checks. Start with provider features disabled/unconnected until current consent/setup is proven. Verify workload MI can pull images/read only its exact secrets and send/receive only its owned event entities.
9. Bootstrap an authenticated pinned OpenFGA store/model using existing service-owned tooling after the private engine starts. Verify permission revocation/cross-tenant denial and stale tuple barriers before permitting user requests. Model/store IDs and event consumers need qualified configuration, not random placeholders.
10. Enable Front Door Premium/WAF with distinct frontend/API origins. Match each pending managed-environment Private Link request to this named deployment and **explicitly approve only those requests**; do not broadly approve unrelated requests. DNS TXT/CNAME ownership and managed TLS certificate validation are external gates. Direct origin public access must fail. Test `/internal/*` blocks, callback/webhook raw-body signatures, query/body bounds and origin-host certificate validation. [Microsoft Front Door private-origin procedure](https://learn.microsoft.com/en-us/azure/container-apps/front-door-custom-virtual-network-private-link).
11. Verify all real redirects under the stable owned hostname: WorkOS browser login/refresh, calendar OAuth state/finish, Recall webhook and calendar push bases, approved provider callback paths and notification links. The template includes optional custom-domain resources but cannot transfer a provider-owned `*.run.app` hostname or add unimplemented callback handlers. Do not promise zero provider reconfiguration where a provider-owned old hostname must change.
12. Perform live qualification, authorized text-data migration rehearsal, restore/tombstone replay and rollback. Only then cut over DNS/users from the retained legacy application. No automatic data import, embedding rebuild, production overwrite or DNS switch happens in this template.

## Release checks and stop conditions

- Qualify five concurrent captures, ten admitted meetings per Meet/Zoom/Teams plus blocked/waiting/removal/end paths; full-duration transcript coverage and late draining; honest partial/gap output. Capture ack/status/summary qualification targets remain the master plan's measured targets, not infrastructure guarantees.
- Exercise Account membership/session/capture consent revocation, private customer/project sharing separation, current source checks in chats/exports/preparation, changed approvals and external-write uncertainty. Use scoped controlled accounts and never trigger unauthorized connector writes.
- Replay duplicate/out-of-order broker/provider notifications, expired cursors, calendar cancellation/rescheduling/reused links, lease expiry, database outages and warm replica replacement. Verify failed deliveries dead-letter safely, and operator replay cannot duplicate paid/provider operations.
- Measure event outbox age, worker lag, capture health, quota denials, model estimates versus provider billing and safe code-class telemetry. Set queue/capture-health alerts with reviewed delivery recipients; source templates do not invent alert thresholds or send emails.
- The current Log Analytics cap/retention is an initial bound, not a GDPR retention proof. No transcript/token/query logging; Front Door/WAF request diagnostics remain off until redaction proof. Test malformed/excessive webhook requests against WAF without turning protections off broadly.
- Private PostgreSQL **TLS/actual Azure administrator privileges**, per-role startup, PG HA failover, public denial, secret rotation and connection budgets are staging gates. The local SQL fixture is ordinary PG17, not Azure's `azure_pg_admin` implementation. Never bypass a failure by making databases public or elevating runtime roles.
- PubSub REST must deny public access while authorized WSS clients work; native negotiation/adapter and revocation still need implementation/qualification. Blob access must remain MI/private/text-only; native Blob adapters are a separate outstanding slice. Domain-level realtime/storage claims are blocked until these work end to end.
- Restore each owning database, replay deletion tombstones before serving reads, verify no deleted transcript/vector/chat/export resurrection. PostgreSQL backups retain their disclosed 14-day schedule; deleting source rows does not erase retained backups immediately. Text Blob versioning/soft delete are disabled here to avoid additional retained copies, but migration data/exports still require owning deletion qualification.

## Rollback and operational discipline

Promote backward-compatible schemas before new runtimes; immutable images permit traffic rollback, **not data rollback**. Use expand/contract migrations and retain old compatible readers until the rollback window closes. Keep old application/data available until restore, permission and end-to-end capture checks pass. Unknown paid/external operations are reconciled, not replayed blindly after rollback. Do not use complete-mode deployments, recursive resource-group deletion, password reset or database recreation as a rollback mechanism.

The first stack assumes Azure public cloud, one regional VNet and one cell. Adding other cells requires a reviewed non-overlapping address plan, Account directory assignment, private RPC routing and separate service stores/keys; never point one cell at another's database. Redis/Live/Search/desktop/media resources are intentionally absent.
